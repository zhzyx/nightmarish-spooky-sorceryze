# 奥林匹斯代码与业务协同规范

版本：0.2。性质：专项规范草案。加载条件：变更代码、接口、数据或业务规则时。

按需参考依赖：specs/concurrency.md。仅加载与当前职责有关的部分；不要求每个执行任务读取全部依赖。

## 代码与业务耦合协同

代码协同同时检查文本、接口和行为。不同文件没有文本冲突，也可能共同破坏伤害计算、经济规则或任务状态。

| 冲突层次 | 示例 | 协同机制 |
| --- | --- | --- |
| 文本与结构 | 同一函数被修改，符号移动或删除 | 版本差异、语法分析、人工或自动合并 |
| 接口与数据 | 事件载荷、组件 API、存档格式改变 | 契约检查、消费者清单、兼容与迁移方案 |
| 行为与业务 | 伤害与护盾分别改动后重复减伤 | 业务不变量、集成测试、仿真及设计判断 |
| 跨域引用 | 代码引用的动画事件或场景节点变化 | 代码与资源依赖检查、运行验证 |

按战斗、角色控制、任务、背包等业务边界登记接口和负责人，但不要求所有客户采用同一拆分。私有实现变更可以局部并发；公共接口变化需形成影响报告并协调消费者；跨模块重构先确定迁移顺序和临时兼容方式。

AI 代码生产以受限变更为交付，遵循客户技术栈、代码规范和生成代码区域规则。预期写入范围与实际差异不符时重新检查授权及影响。自动合并只适用于能证明兼容的范围；语义不明的冲突不得由文本合并结果直接判定成功。

测试按风险选择语法与类型检查、单元、契约、集成、存档兼容及玩法回归。代码、配置、场景和运行资源作为同一个候选项目版本验证。只验证生成分支、随后直接合入已变化的主线，会留下集成缺口。

例：任务 A 修改伤害结算，任务 B 修改护盾，任务 C 修改 HUD。A 与 B 因共享战斗规则进入同一候选集成组，验证减伤与边界不变量；C 可先独立开发，但其数据契约变化时需进入关联验证。发生争议时由战斗领域负责人判断，不能由三个执行者各自确认整体正确。
