# 司南｜共工统一工单管理规范

性质：共工核心通用 Agent 司南的任务协调专项；入口为 agents/sinan/AGENT.md，工具目录 modules/sinan 是实现支撑，不是用户接入子模块。按各类任务总协调、跨业务依赖与交接职责加载；共同治理及状态规则直接继承，不批量加载整个框架。

司南覆盖所有业务任务类型，包括独立事务；类型可扩展，开发类仅是其中一部分。Feature、代码与设计版本按业务适用，完成条件依据任务成果与真实委托确定。既有账本保留唯一工单事实。总协调管理来源登记、全局身份、协调关系和派工候选，不维护竞争的执行状态。全局身份为账本稳定 ID 与工单 ID 的组合；共享任务只建一次，流程 plan 不默认充当 Feature。

总协调处理跨项目依赖、优先安排、阻塞责任与交接；相应业务主责负责整体成果，偃师按适用职责负责设计交付，夸父负责阻塞、重复停滞及升级质量事件的分析和优先处置，验证者和交付负责人保留其原有判断权。新增职责按实际委托分配，不因此新增固定 Agent。

派工前检查硬依赖、源版本和证据有效性；环、缺失依赖及失效证据阻止受影响正向推进，无关分支继续。退回修复不应因前置质量失效而被阻断。优先级与计划不授予权限，委托记录不等于实际执行，子项完成不等于整体目标达成。

当前通过已有元衡来源的只读总览与原命令准备接入；这是适配器现状，不限制业务任务类型，其他来源需适配后才能纳入真实覆盖。具体入口由 skills/work-order-coordination/runtime-ref.json 指向交付模块；该绑定不包含框架副本。所有源账本写入、派发与验收继续由原 CLI 和宿主处理，并在执行时重新检查跨账本约束。未登记或无法读取的来源不宣称已覆盖，不能以空总览代表全部项目均无任务。

详细对象、生命周期、用户呈现及适配边界按需见工具模块中的《工单管理体系》。迁移时更新真实绑定，不把业务设计文档变成全部 Agent 的默认提示词。

司南标签分为类型、源进度、判断与业务分类：Bug 与处理中可并存；源进度自动派生，协调标签可维护且保留变更记录。待判断须列明责任人、事项及是否阻塞；普通判断留在授权主责，阻塞、重复停滞、关键问题及跨业务质量交夸父，用户保留取舍才提交用户。标签不能替代元衡判断或改变源验收。类型补标、标签筛选和本地协调记录写入按需查工具说明，不增加默认 Skill 指令。

## 事件触发与同步

### 新需求进入工单

宿主收到实际新需求时，保留原始诉求、来源事件 ID、宿主核验的工作者／执行实例、授权范围与稳定需求标识。先在适用的权威来源按稳定标识和目标查重：同一需求的澄清、范围变更与重试关联原工单并保留版本；只有独立交付目标才新建工单。需求整理可提出标题、类型、范围、验收和待判断项，但提案不是权威工单，Agent 判断也不授予写入权限。

若确认新需求且来源写入已获授权，由宿主调用该来源的原入口创建工单，回读稳定工单 ID、版本及实际状态，再提交 `request.created` 给司南刷新和协调。创建回执不明时先按需求标识对账，禁止盲目重建；来源不可用或权限不足时保存待关联记录、责任人、证据、可继续工作和恢复事件，仅挂起依赖该工单的执行。未取得权威工单回读前，不把提案、文档或聊天快照记为已建单，也不启动要求工单绑定的生产执行。

共工核心只要求适用的权威工单来源，不指定 GitHub。当前本地司南工具只读已登记元衡来源，不替宿主创建工单；其他来源先具备真实适配、身份与回读能力。当前工作区 已接入 Git 时，由其 Git 子模块按同仓库规则查重、创建／关联并回读 Issue，再将事件交给通用司南；Issue 号码、标签和 Git 状态不是共工通用工单字段。只读咨询是否需要外部 Issue 由该接入的明确契约决定；咨询不得因此获得写文件、生产工具或后续执行权限，转为执行时重新核验工单及授权。

司南作为核心通用协调 Agent 保持按需可用。触发来自实际新需求、工单进度变化、依赖变化、用户或有权主体决策、执行完成／失败回执以及用户主动查询。时间流逝不构成触发：废止定时扫描、轮询、heartbeat、cron、延时唤醒和按时间重试。历史归档中的此类入口不可沿用。

事件由当前宿主或实际接入方在同一次工作中交给司南；没有全局事件监听器，不声称自动捕获其他聊天或外部系统。登记来源的执行者提交状态变化时必须同步交接司南；漏报在后续真实事件或用户主动对账时处理，不用定时兜底。

处理顺序：核对真实事件来源、工单全局 ID、当前源版本与权限；需要改变源状态时先通过原 CLI 持久化并取得回执，禁止根据消息直接覆盖源账本。随后读取最新来源，更新标签、进度文档、依赖／阻塞、责任人和下一步。任务专属文档只更新本次受影响且获授权的部分，保留来源引用与验收证据。候选、提交、完成执行、验收通过分别记录，文档是源状态的视图，不另建状态账本。

`runtime-ref.json` 的路径以框架根目录解析。`coordinator` 提供 board／ready／label／prepare；`refresh` 提供单次事件刷新：`node modules/sinan/refresh.mjs <事件类型> <来源引用> [登记表路径]`（在框架根运行；其他工作目录使用解析后的脚本路径）。类型为 request.created、ticket.changed、dependency.changed、decision.recorded、execution.finished、execution.failed、user.requested。该命令读取登记来源，并原子更新登记表同目录的 progress.md，覆盖状态、标签、责任、阻塞、验收与源版本；不写源账本、不启动 Agent、不上报虚假的谛听回执。默认登记表为空，不能据此宣称所有项目无任务。

刷新后，仅在有就绪任务及真实授权时安排派发；先短事务保存原 CLI start，再启动宿主实例并写 ack，回执不明不重派。独立任务先派出再回收，沿用两个执行槽、一个独立审查槽及真实宿主容量／读写冲突约束。完成、失败、依赖解除等事件触发补位；无就绪任务则结束，不安排下一次时间唤醒。自动派发指此事件内的授权协调，不是定时自动化。

实际业务调用仍必须按 reporting.json 接入共享谛听，事件与真实源／执行快照关联，同一事件不重复计量；文档更新记录不能冒充谛听落库回执。采集失败保留待处理事实，在后续实际事件或用户请求时重试；未接通的数据源或用量保持未知。

## 关联文档与完成事件

交付核验及版本／采集状态依据 specs/delivery.md。scope.changed、release.completed、source.changed、report.delivered 同样触发一次刷新：范围变化更新验收约定，发布完成对账交付状态，上游变化列出受影响依赖，采集回执到达更新相应证据。来源事件不是新的任意任务授权。

登记表可配置 `document_sync`：`path_base` 固定为 `registry_directory`，`write_root` 是明确授权的相对文档根，`documents` 每项为 `{path, tickets, parent_tickets?}`。所有路径统一相对登记表目录解析，文档必须落在 write_root 内；工单使用全局 ID，父工单也须列入 tickets。文档必须预先存在，并含唯一的 `<!-- sinan:begin -->` 与 `<!-- sinan:end -->` 标记对。刷新只替换标记内的派生视图，保留正文和用户决定；不以整篇重写替代同步。

刷新从权威来源派生状态、标签、责任、依赖、阻塞、验收与下一步，同时输出登记表旁的 `sync-result.json`，分别列出本地已同步／未同步文档、来源缺口、外部权威操作待办及本地写入失败。单文件原子写入不等于所有文档或外部系统同时成功；部分成功按实际结果报告，后续真实事件可重放修复，标记区不重复追加。

父工单的验收和关闭取自原来源，子项完成只触发父项重新判断。外部 Issue、标签和上级状态由原连接器及真实授权更新并回读；本地刷新工具不写外部 Issue。未完成同步必须留在待处理结果中，不因已提交代码或已更新 progress.md 而宣称整体闭环。

新建需求／交付文档将会变化的状态集中放在同步标记区，不在正文维护另一份当前状态。历史判断保留其来源版本和时点；范围或批准变化时，由责任方核对正文中的现行承诺，并通过原连接器修正外部过时说明。采集索引逐来源维护配置、排队、交付与消费状态，不使用一个总开关代表所有来源。

## 局部挂起与持续推进

对话缺信息、待判断、待决策、工具失败、采集/同步失败都不能使整个框架停止协调。每次真实事件先分离受影响操作与可继续工作；记录原意、证据、影响范围、责任方、下一步和恢复事件，在适用的本地权威来源查重并关联工单。仅已授权接入 Git 的具体任务按子模块契约关联外部 Issue。独立交付才拆子单，同一问题沿用原单；父项尚有执行工作时保持处理中，局部待决策用问题记录表达。适用外部来源不可用时先持久保存待同步记录，后续真实事件补写并回读，不伪造 Issue 编号或重复派发。

普通判断由已有授权主责处理；技术问题交业务 Agent，阻塞、重复停滞、关键问题及跨业务质量交夸父，司南负责协调与回收。用户保留的决定异步提交，负责人继续准备事实、备选方案和其他任务，不能把沉默当批准。未认领问题由当前宿主协调者负责；登记 owner/proposed 不等于 Agent 已执行，真实 start/ack 才算派发。没有可用授权实例时保留适用的待派发工单并释放执行槽，不能无限等待或创建未经准入 Agent。

`pending_user` 仅表示待用户决定，不自动排除就绪或撤销验收。确实依赖该决定的操作须显式设置 `pending_user_blocking: true`；`assessment.blocking: true` 同样只限制该工单正向推进，仍生成问题处理候选。不得为绕过权限把真实限制改为 false；应拆分已授权调查、修复和独立交付。硬依赖、无效证据、源 blocked、授权/预算/数据边界与冲突锁只限制关联操作，不能以继续推进为由宣称通过或重复执行不明回执。

board/refresh 的 `followUps` 是派生交接队列，包含稳定问题键、源工单、责任、适用时的 Issue 对账动作与恢复事件；当前宿主向对应已授权 Agent 派发，已授权 Git 接入的任务才使用原连接器关联 Issue。工具本身不写远端或启动 Agent。`issue_ref` 可保存已回读的关联引用。此队列不与权威工单来源争夺状态。无就绪业务任务也先处理问题调查/交接，再结束本次事件；后续证据、决定、依赖、执行回执或用户请求触发重试，不使用定时轮询或空转。

单文档缺标记、读写失败返回 `outcome: partial`、`updated: false`、逐项错误及修复候选，继续其他安全文档；调用方必须检查结果而非只看退出码。越界、源账本保护、重复输出、锁冲突与登记结构无效仍拒绝本次危险同步，不扩大写权限；宿主将该错误关联适用的本地工单，已授权 Git 接入时再关联外部 Issue，继续其他安全任务。runtime/runner.py 的失败/需对账结果也按此交接，不盲目重试模型或工具调用。采集仍区分排队、落库和消费，故障不能伪装完整观测。
