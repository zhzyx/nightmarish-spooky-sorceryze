# 共工模块系统规范

版本：0.3。性质：专项规范定义。加载条件：评估、开发或组合生产模块时。

按需参考依赖：GOVERNANCE.md。仅加载与当前职责有关的部分；不要求每个执行任务读取全部依赖。

## 模块划分与产品组合

### 核心、业务能力与接入实现

核心定义稳定职责、语义契约和治理边界；业务模块表达要完成的能力；接入子模块把能力映射到特定来源、工具、引擎、平台或设备。模块不是 Git submodule 命令，也不要求独立仓库、进程或 Agent。当前一个实现文件可能承载多个子模块职责；逻辑归属不等于已完成代码拆分。

偃师负责需求、设计、决定与验收内容，不规定文件扩展名和保存位置。司南负责工单身份、依赖、交接与事件协调，不规定 GitHub Issue。合契负责多方变更比较与整合，不规定分支和 PR。谛听负责记录语义与证据，不规定 Git 文件存储；治理和质量责任同样不因接入变化而转移。

文档保存、工单来源、版本协作、交付存储、采集存储、模型传输、引擎操作及平台部署分别按可替换能力划界。Git 仓库内 Markdown 文档、GitHub Issue／子 Issue、Git 提交／PR、Godot 编辑与构建是具体接入；“生成了需求”不等于“已写文件”，“提出子任务”不等于“已创建远端子 Issue”，“形成候选”不等于“已发布”。

依赖方向为接入实现依赖核心契约，宿主按任务绑定实现。核心 skill 不加载未选接入的提示、配置、工具或强制环境前提；新增接入优先新增模块及绑定，不复制核心 skill 或改写治理。确有共同语义缺口时单独形成契约修订候选，核对消费者兼容性后才更新核心。平台专用错误只阻塞对应操作，不影响其他已授权能力。

物理边界：核心定义仍由 CURRENT_FRAMEWORK.json 定位；接入定义与宿主组合在仓库根 customizations/ 下管理。framework/ 中历史随包交付的专用实现按职责归属接入层，不因目录名称成为核心。本次仅定义结构，不搬迁文件或改变有效发布；源码迁移另行核对路径、依赖、指纹、准入与恢复。当前具体清单见 [接入子模块边界](../../customizations/module-boundaries.md)，路径相对本文件。

### 新平台、设备与工具按需发现

本规范面向可扩展的平台与设备类型，不宣称已适配所有平台。收到实际需求、环境变化或能力失败事件时，由当前宿主和主责检查所需能力与已登记模块；不增加周期扫描。比较能力及契约版本、工具／服务身份与版本、执行宿主和目标平台、设备限制、权限、数据边界及适用验证证据，不能仅按产品名称匹配。

区分四种结果：兼容且已验证则复用；实现兼容但参数不同则新增配置；缺少能力或语义映射则建立接入子模块候选；能力存在但环境、权限或证据不足则登记对应缺口，不能误判为必须新建模块。状态分别保留未接入、候选、范围内已验证、该宿主已启用、不兼容／停用；注册、验证和启用不可互代。

新候选只覆盖当前需求的最小能力，声明输入输出、读写和权限、依赖与兼容范围、负责人、路径解析基准、取消恢复、谛听绑定、代表任务验收及失败语义。固定任务所用版本，验证成功、失败、取消／恢复及未选择模块时不改变其他能力。未支持项显式返回限制；通过适用审查和精确准入、取得实际宿主授权后再绑定，不因生成目录或清单自动加载执行。

优先由已有 Agent 承担需求定义、协调、接入实现和验证；模块与 Agent 不一一对应。只有复用不足、专业分工或必要独立审查有具体收益时，依据 agent-organization.md 形成临时子 Agent 委托，明确成果、权限上限、读写范围、交接、验收与撤销，并执行 governance-review.md 及 reporting.md。生成候选不等于实例化，子 Agent 不得批准自身准入，始终受元衡治理。

平台描述区分执行宿主与交付目标；按实际需求记录 OS、架构、运行时／工具链、设备类型、输入方式、显示、网络、存储、资源及沙箱限制，不枚举所有组合、不按操作系统机械复制模块。相同契约优先配置差异，行为或权限模型确有差异才独立实现。跨设备证据只覆盖实际验证范围。


模块表达可复用能力；工作流表达能力如何组合；Agent 表达当前由谁执行。三者独立配置。设计、生产、质量是工作主线，不是必须常驻的部门，也不要求每个任务走完所有环节。

质量主线包括规格检查、生产过程检查、资产检查、工程检查、玩法回归、场景验证、体验评估及交付验收。它既提供独立模块，也可以接入客户现有验证服务。

平台底座包括企业与项目配置、知识与实体关系、能力注册、任务调度、资产与配方、版本协同、模型工具路由、质量证据、成本资源、权限隔离和能力评测。客户可以不启用某个专业模块，但平台必须保留相应的输入与验收责任。例如，客户可自己提供资产规格和质量报告。

支持三种交付方式：在引擎内完整使用；将独立能力接入客户现有管线；与客户工具混合编排。引擎适配器是执行游戏工程操作时的依赖，纯资产加工或独立文档任务不必启动引擎。

## 模块契约与配置边界

模块内生成 skill 与 Agent 定义时执行 specs/governance-review.md 的回查；普通模块需求、代码或资产生产不触发该审查。新入口保持精简，外部 Agent 合入分别取得框架审查与元衡评价结论；缺少证据或纳管状态不完整不得启用。

每个现有及未来子业务模块必须继承元衡统一纳管约束与冻结纲领 1.0。模块契约须声明其 Agent 的登记与派生规则、治理关系、授权来源和撤销方式；外部 Agent 也必须通过纳管后接入。客户裁剪、替换工具、私有化部署或引擎迁移不得关闭该约束。缺少纳管声明、试图脱管或要求改写纲领的模块，不得通过准入。后续业务能力进入新模块或专项规范，不修改基础纲领。

每个模块注册时声明：标识与版本、输入输出结构、必需依赖、可选增强、可替代外部能力、读写对象、权限、预算、运行环境、取消与恢复方式、验收规则、兼容范围和负责人。依赖约束与商业套餐分别管理。

模块输出包括产物本体、源文件或可编辑参数、生产配方、版本来源、依赖、证据和待处理问题。生成失败可以改用模板、程序化工具、已有资产或人工制作，替换路径必须保持交付要求。

模块组合规则区分五类：必需依赖缺失则不能执行；可选增强缺失则按声明降级；外部能力可以通过契约替代；互斥能力不能同时生效；版本不兼容需转换或调整。降级行为需可见，不能暗中降低客户的质量承诺。

配置按平台、企业、项目、工作流和任务分层继承。下层可以在授权内细化约束，不能覆盖上层的权限和根本边界。配置记录来源、生效版本、兼容检查及恢复点；在途任务固定所用版本，变更后明确继续、重验或取消策略。
