# 同一 Issue 的多人提交、差异比较与冲突解决

路径以仓库根为基准；仓库路径以宿主绑定的 repo_root 为基准。仅已绑定 Git 接入时加载；复用 git-workflow.md 的身份、权限、采集和司南接口。本流程由受委托合契实例操作已有 Git 工具，不是后台监听、服务器锁或自动取得仓库权限的服务。

本篇的一单多贡献和外部回读用于已授权 Git/Issue 接入的任务，不将外部 Issue 变成共工基础前置要求。仅本地工作的适用工作记录可以承载贡献映射、差异与冲突证据；不得为了运行本地比较而擅自创建外部 Issue。当前工作区 的外部 Issue 要求由其自己的接入规则执行。

## 一单多贡献

Issue 是共同目标及验收载体，不是一位工作者的排他锁。每份贡献保存 contribution_id（仓库身份、账号、execution_id、change_id）、commit/PR 来源、不可变 tip SHA、目标分支/目标 SHA、作者声明与已认证来源、实际 merge-base、文件与重命名清单、读写权限、验收项、验证回执。commit author 只作来源说明，不能证明当前认证账号。分支名或 PR 号不能代替内容版本；PR 更新后产生新快照。

司南在原 Issue 的追加事件中汇总贡献，合契保留本轮读取的贡献集合及来源版本，不维护竞争的完成账本。Issue 相同不意味着补丁相同；仅重复事件按稳定 event_id 去重。相同 SHA 可标记已观察，同补丁不同 SHA 仍需检查上下文、依赖与效果，不能只凭 patch-id、文件名或标题自动删除贡献。

## 比较与整合步骤

1. **固定输入**：按授权从仓库服务回读贡献/PR，并只向自身本地获取所需对象，记录获取通道。核验目标 SHA、各 tip、原工作区/index 和声明范围。没有可访问的提交先记录该贡献待补证，继续已知输入分析；不能访问贡献者本地目录。远端 Git 认证未核验时只使用已授权可验证的本地对象。
2. **求共同基准**：对目标候选与每个 tip 运行 merge-base 并保留结果。缺少对象、没有共同祖先或多个 merge-base（交叉合并）时，不任选一个作可信三方基准；交授权主责确定整合策略，继续其他贡献的比较。已在目标祖先链中的提交标记 already_included，仍核对所需效果和验收，避免重复 cherry-pick。
3. **生成差异清单**：读取 base→目标和 base→tip 的 `diff --name-status -M`、具体 diff 及必要的二进制标记；多贡献两两识别文件/重命名重叠。分别标记独立修改、相同修改候选、文本冲突、删除/修改、改名交叉、二进制/生成物，以及接口或配置之间的语义冲突。不同文件或 Git 无冲突不证明语义兼容。
4. **自身副本整合**：使用宿主授权的独立本地候选目录/分支，不覆盖原有脏工作区或混入无关 index。保持可恢复的输入 SHA 和整合顺序，每加入一份贡献后重新计算与当前候选的 base/diff；不能把 N 方冲突仅按最初两方结果处理。按仓库约定选择保留历史的 merge 或明确授权的其他方法，不擅自重写共享提交。自动合并只是候选，失败保留冲突证据。
5. **解决技术冲突**：逐文件保留 base/ours/theirs、冲突块及双方意图/验收依据。在当前授权范围内由合契编辑候选，组合兼容行为并记录取舍；禁止整文件无依据选 ours/theirs。改名/删除核对意图，二进制/生成物按责任方确认的版本或生成流程重建。产品语义、权限或验收选择不明确时，只挂起对应文件/整合动作，交司南记录负责人与恢复事件，并继续不受影响的差异分析、测试或独立候选。Git merge 尚未结束的 index 不能用于另一个无关提交；独立工作在另一个授权候选中继续。
6. **验证结果**：检查无未合并 index 条目、无遗留冲突标记（结合文件语法，不能只靠文本搜索）；审阅候选相对目标以及每个贡献的差异。运行各贡献验收和组合回归，检验双方必要效果是否保留；记录未纳入内容及原因。通过后才提交精确候选。代码行无冲突、merge 返回成功或编译成功均不能代替业务验收。
7. **交接和目标漂移**：记录输入 target/tips、最终 commit/tree、贡献到结果的映射、解决说明、验证摘要和未决项。发布前回读当前目标与贡献版本；变化使受影响的整合/验证过期，保留原候选后增量重比，不强推覆盖。对于一个目标分支，可由一个获授权整合者串行发布已经并行产生的候选；这不限制多位工作者向同 Issue 提交贡献。远端更新仍可能竞态，以服务端非快进/版本保护与操作回执判定，失败回到比较步骤。

## Issue 交接与关闭

每个贡献分别记录 observed、compared、candidate、conflicted、integrated、validated 或 deferred 的证据；这些是原 Issue 事件的派生视图，不是独立状态权威。合契将比较、冲突、解决与验证回执交司南，贡献者完成只改变该贡献的观察状态。

整单完成要求本轮明确验收范围内的贡献全部纳入并通过组合验收，或有权主责明确拒绝/延期并留下原因；尚有必要冲突、未知依赖或待验收贡献时不能因一个 PR merge 就关闭。后续新贡献事件按当前范围判断重开原单或关联后续单，不静默丢弃或自动扩大原验收承诺。

## 固定提交的并发准备清单

从仓库根运行 `python customizations/platforms/development/git/heqi/integration_plan.py --target origin/main`，枚举该提交的全部 Git 跟踪对象、对象 ID、大小、根目录和扩展名。输出不包含未跟踪文件或其他工作副本，也不表示已逐行审查源码。完整清单可重建，不必随每个 PR 提交一个全仓共享清单。

加 `--contributions contributions.json` 时读取贡献数组，例如：

```json
[
  {"id": "renderer", "tip": "FULL_COMMIT_SHA", "reads": ["servers/rendering", "core"], "depends_on": []},
  {"id": "docs", "tip": "FULL_COMMIT_SHA", "reads": [], "depends_on": []}
]
```

文件路径相对仓库根，输入 JSON 路径相对命令调用目录；`--repo` 可明确指定工作树。`reads` 是经责任者核对的完整读取依赖路径或目录前缀，不是 glob；省略或 null 表示未知依赖，不能声称独立。空数组只适用于已确认没有其他仓库读取依赖的贡献。`writes` 从真实共同基准到 tip 的 Git 差异计算，不采信调用者的写范围声明。改名保留源删除和目标新增，文件/目录交叉也视为重叠。

对贡献 i、j，文件层准备并行的必要条件为 `W_i ∩ W_j = W_i ∩ R_j = W_j ∩ R_i = ∅`，且依赖贡献已在前序准备批次中。这里的交集包含路径前缀重叠。该条件不足以证明业务语义兼容。算法按输入次序确定性分批，不保证最少批次数；缺对象、多个 merge-base、未知依赖引用或依赖环拒绝计划。相同 tip 的不同贡献保留各自身份。

`preparation_waves` 仅供并行比较、构建准备及评审分配；不是发布队列、已验收依赖或启动授权。每份贡献分别绑定 target/base/tip；target_overlap 提示与主线变化的已知读写交叉，target_dependencies_unknown 保留未知读取影响。主线或贡献推进后重新生成，最终仍须对整合候选执行组合验证、精确 CI、发布前远端回读及真实权限检查。不以空交集复用旧候选的成功证明。

此工具是既有 Git 宿主中的 Python 标准库 CLI，不嵌入或链接引擎；输入为本地 Git 对象和显式贡献 JSON，依赖 Git 可执行程序，不调用网络或修改 index/worktree。回退为停止调用并继续上述人工比较入口。测试入口为同目录 `test_integration_plan.py`；测试使用临时合成 Git 仓库，不宣称跨账号或远端合入验收。

## 代表验证

本地测试仓库中可用两个不同 author 模拟两份贡献，但必须标记合成贡献者，不能宣称验证了真实双账号认证。至少验证：同 Issue 的独立修改合并后两者均保留；同一文本块冲突经语义解决保留双方行为；目标已含贡献时识别祖先避免重复；无文本冲突但组合行为不符时仍拒绝通过；二进制/删除改名冲突局部挂起；目标或 tip 推进后旧验证失效。记录真实 Git 命令与结果，和纯推演场景分开。
