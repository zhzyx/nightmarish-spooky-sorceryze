# Git 接入：本地协作与司南契约

仅在宿主明确绑定 Git 接入时加载；这是当前工作区的接入方式。通用职责与必填字段见 framework/agents/heqi/references/workflow.md，本文件的账号、仓库、Issue 和提交字段只约束 Git 适配任务。

路径基准：仓库根；仓库文件路径另以实际委托的 repo_root 为基准，repo_root 由宿主显式绑定，不跨工作者目录。工作者身份为 Git 服务认证 login（当前 GitHub 适配使用 gh api user），数字账号 ID 可作改名映射辅助。一个账号作为一位工作者是用户约定，不声称账号一定对应现实中的唯一自然人。

gh api user 只证明该 CLI/API 通道的账号；Git fetch/push 可能使用不同的 SSH 密钥或凭据助手。远端操作前核验目标 remote、目标仓库及实际认证通道与 account_login 的绑定，记录脱敏身份回执，不采集密钥或令牌。不一致或无法核实时仅挂起该远端操作，不能用 commit author、git user.email 或另一个 API 登录冒充 push 身份；已明确授权的本地调查继续。

## 责任和入口

司南负责适用工单的去重、状态、依赖、责任及派工。已授权 Git 接入时，一个外部 Issue 可关联多个账号、执行实例、变更集、commit 和 PR；去重对象是重复工单/重复事件，不是不同贡献。合契负责当前工作者可访问的已共享提交差异、文件重叠、冲突解决候选和提交证据，执行 concurrent-issue.md。业务 Agent 负责成果，独立审查方负责评价。可选 git-issue 模块负责适用任务的预览/创建/复用；未启用 Git 接入的共工框架工作不要求外部 Issue。两者都不能改写元衡源账本来伪造 GitHub 覆盖。

Git 协作委托至少提供：account_login、identity_receipt、repository、repo_root、work_ref、execution_id、change_id、base_commit、read_paths、write_paths、authority_ref、预算、交接对象、完成条件；已授权使用外部 Issue 时另提供 issue_url，未接入时 work_ref 指向适用本地记录，不伪造 Issue 或默认对外建单。下述 Issue/PR 操作仅适用于已授权接入的来源，本地比较/候选记录仍可按原权限进行。本地路径必须落在明确授权根内，识别 symlink/junction 与仓库嵌套，不能通过链接绕过边界。读取同工作者其他聊天产物也先核读写范围。

## 生命周期

1. **观察与认领**：通过原连接器回读 Issue/已有认领及其版本；本地读取 status、diff、暂存差异、HEAD，保留原有脏文件清单。登记 change_id + account_login + execution_id + base_commit + 文件范围。没有其他工作者的新鲜状态时标未知，不声称无人编辑。
2. **协调并行**：文本可合并工作允许并行但记录重叠；二进制/生成物或不可合并范围提议单写者并记录双方确认。两个认领同时到达时不以最后评论覆盖前者，由主责在 Issue 追加明确裁决。等待中继续非冲突范围，未确认不声称取得排他权。已有锁只记录验证回执，不替他人解锁。
3. **本地实施与核对**：改动前后比较本变更集范围。发现未声明的新建/删除/改名时先 reconcile 范围；禁止用 git add -A 把无关改动混入。授权内从共享仓库获取更新到自己的本地记录，不能重置别人的工作区。仓库无 Git 或无可核验基准时先输出准备/调查项，不伪造 commit。
4. **搁置与审查**：可将自身精确补丁、分支或 draft PR 作为待审交接；本地 stash 仅本地，不能描述为共享 shelf。应用他人已共享成果时只在自己的授权副本预览/验证；不得覆盖自己的未保存成果，也不得回头修改对方本地文件。
5. **比较与解决冲突**：同 Issue 的各贡献先分别比较共同祖先至各方 tip 的差异，区分已包含、相同补丁候选、独立改动、文本重叠和语义冲突。保存 base/ours/theirs 证据，在自身授权副本按明确顺序整合多个提交；合契在已授权且验收明确时实际解决技术冲突，逐块解释取舍并运行受影响检查。文本合并成功不等于语义通过；二进制由责任方选择来源或重做。改名/删除/生成物冲突单独认定。涉及目标/权限取舍交用户，技术判断交授权主责。
6. **提交与交接**：重新回读远端目标、候选和暂存摘要。当前变更集/HEAD/文件漂移时重核，只暂存已核定内容，清单中有冲突或未审内容不得提交。提交失败保留工作与证据；push 遇非快进时 fetch 后重核，不 force、不改写他人历史。成功后回读 commit/tree/PR 与Issue关联，交司南更新进度。业务验收仍由原主责，不自动关闭父单。

## Issue 协调记录

使用追加评论/原工单事件，记录 event_id、account_login、execution_id、change_id、base_commit、files、phase、prior_revision、observed_revision、decision_owner、evidence_refs；这些字段是观察与责任认定，不提供 GitHub 字段原子比较交换。写入前后回读发现别人变化时追加冲突事实，不整段覆盖别人正文。重复事件以稳定 event_id 识别，不重新派工；删除/转让认领需原主责或有效裁决并留下历史。

多人提交按 contribution_id 保留各自 tip/PR、目标基准、整合结果和验收关系；多位贡献者可以共用同一 Issue，整合责任人与贡献者分别记录。首个 PR 合入或贡献者宣告完成不关闭整个 Issue，司南按本轮贡献快照与验收范围汇总。未知在途贡献保留未知，不推断所有人已完成；新贡献/目标推进事件触发增量比较。

谛听保存 source、实际 Agent 快照、request、step、message/handoff、quality/rework 和 coverage，通过既有 reporter；工单仍是状态权威。未送达事件可持久排队后按真实事件补交，不用定时扫描；回执不明不重复提交或推送。没有实际在途工作时结束本次调用。

## 代表场景验收

| 输入 | 应有行为 |
| --- | --- |
| 同账号两个聊天改同文件 | 同一工作者、不同execution/change；保留脏改动，协调自身变更集，不能当成两个人 |
| 不同账号修改文本 | 只在当前账号本地准备三方合并；Issue记录对方认领，不访问其本地目录 |
| 两人同时认领二进制 | 认领冲突交司南主责裁决，未确认不得称已锁定；其他文件继续 |
| 暂存区含别人的改动 | 不提交整个index；先与自身变更集核对并隔离，未经授权不unstage或stash别人内容 |
| 远端推进/非快进 | 自身本地取新基准、解决与重验，不强推；保留自己的候选 |
| Issue并发评论/账号标记伪造 | 认证账号与声明区分，保留两条事件并回读；不把最后写入当授权 |
| 授权路径链接到其他人的目录 | 拒绝受影响写入并记录问题，不以可访问性当权限 |
| 用户尚未决定 | 只挂起相关文件/发布操作，调查、备选方案与独立任务继续 |
