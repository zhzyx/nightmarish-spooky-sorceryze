# macOS 明确重启程序目标修复

稳定需求 ID：`macos-restart-executable-20261107`。Issue：[#212](https://github.com/zhzyx/nightmarish-spooky-sorceryze/issues/212)。

来源：用户报告“mac 编译完成后编辑器自行关闭，却没有重启”，当前 Codex 聊天将底层 macOS 重启目标丢失问题派给独立子 Agent；执行责任为本聊天的 macOS 修复工作者，GitHub 操作者 `kaiyunxue`。本次仅准备隔离候选和真实验证，交回主责任者独立审查；未授权本工作者切换正在运行的编辑器或合入 main。

## 故障与边界

`OS::create_instance()` 的通用实现仅在 `restart_on_exit` 启用且 `restart_executable` 非空时采用明确目标。macOS override 始终选择当前可执行文件或当前应用包，导致退出时交给外部重启守护程序的参数被交给旧编辑器，旧窗口关闭后未启动预期守护程序。

关联 #95 的自更新产物接收判定，但不是同一故障；#95 的既有工作者与范围不变。也不接管 #165 的 AI Chat/CLI 修改、#184 的需求上下文修改，或用户正在运行的编辑器/项目。

本次产物为 `platform/macos/os_macos.mm` 的最小修正、`core/os/os.h` 中只读 C++ 访问器、针对明确重启目标的回归验证及真实来源/验证证据。目标平台为原生 macOS arm64，Apple Clang；不新增脚本接口，不硬编码 Python，也不根据命令行参数猜测重启意图。

## 验收与必要验证

1. `restart_on_exit` 为真且明确目标非空时，macOS `create_instance()` 使用该目标并保留参数及子进程 ID 的传递。
2. 未启用重启或目标为空时，普通可执行文件、应用包和无界面实例继续使用原有路径；应用包内的显式外部目标不被当前包覆盖。
3. 使用本候选编译 macOS 受影响单元，并尽可能通过原生进程验证显式外部目标与普通路径。源代码检查、编译单元成功和真正退出/守护/新编辑器链路的证据分别标明，不将前两项冒充端到端验收。
4. 隔离工作树从已回读 `origin/main` 的 `e9dd3931` 创建；不改动其他工作者副本，不终止现有进程，不启动用户项目副本。

先验证直接故障和普通路径分支；需要完整引擎链接或全编译时，先向主责任者协调构建时间，最多使用 `-j2`。复用已确认的构建参数 `use_volk=yes accesskit=no allow_unsupported_apple_clang=yes`，仅在同一输入和配置下声明证据适用。精确候选的独立审查与后续提交/远端门禁由主责任者接续。

完成条件：隔离候选、必要验证的实际结果和未覆盖边界可复核，并被主责任者接收。未知或受协调限制的端到端项目不标记通过；不把交接当作 main 已交付或原 Issue 已完成。

## 实现与实际验证

macOS 在明确重启目标有效时委托 `OS::create_instance()`，由已有虚 `create_process()` 保留目标、参数和子进程编号；其他 macOS 分支原文保持不变。只读访问器没有绑定到脚本 API。新增 macOS 回归使用 RAII 在任何断言前还原重启开关、参数列表和目标程序。

主责任者批准共享构建窗口后，基于 `e9dd3931d66ad244b88723d32455ca2c6cf4ecf2` 组合本单三份源码与 #184 的最终 v4 三份源码，完成原生 `tests=yes` 编辑器构建。两方源码所有权、固定补丁摘要、逐文件摘要和环境详见 [验证记录](../data-collection/issue212-macos-restart-validation.json)。这份产物用于组合验证，不冒充两份分别提交的候选。

- 完整构建成功，耗时 `00:11:53.91`。#184 的一行测试断言修正后，仅重编译受影响测试对象并增量链接，耗时 `00:00:10.13`。
- macOS 两个测试、三个启动情形、30 个断言全部通过，runner 正常以 0 退出。显式 `/bin/sh` 的实际进程编号和含空格／中文的参数回执一致；普通 headless 的空目标重启与禁用重启两项对照均实际运行临时脚本并正常退出。
