Post-installation preparation recovery, 2026-11-14: an actual accepted missing-execution-evidence review queued existing repairs, but preparation repeatedly failed on a changed source baseline. The original setup/configuration and registered repair predecessors remained available. History-save callbacks retried the failed setup without a new explicit action. The implementation keeps the baseline check and existing repair verifier intact.

Each native preparation records its actual selected producer IDs, parent/conversation/Issue/request/design binding, owner hashes, attempt identity and batch token. Intent must be saved and read back before process creation. Failure is persisted before UI/history callbacks; status, draft saves, configuration edits and cold startup cannot clear it. A process disappearing without a valid actual result leaves an unknown launch outcome. Stop preserves the attempt; late results can settle its recorded outcome but cannot populate a different or cancelled batch or start workers. Another actor, changed binding/predecessor, live process, unknown outcome or changed result remains blocked. A known completed setup does not imply that another worker's lease has been released.

The recovery entry is the existing public Continue Production button (SpawnWorkOrderAgents). After correcting the stated cause and selecting the existing session authorization or explicit configuration, the original parent may request one checked attempt. Registration failure restores the prior participants and gate. Successful registration archives the prior attempt and queues only its exact participants; unrelated interrupted children stay inert. Cancellation and failed attempts are retained, and acceptance/repair budgets are not reset. Unknown launches require actual terminal/lease reconciliation rather than a new automatic launch.

Already registered repairs reuse their original configuration only when every selected item is a repair with matching original terminal, independent review, assignment, configuration path/hash, authority and current runtime/model/capacity selection. Mixed new producers, missing/drifted configuration or lineage are blocked without falling back to initial setup. The hashed native dispatch request binds configSha256; the Node runner verifies the same bytes it parses before any launch, then performs its existing repair/currentness/lease/intake checks. Generated UID drift is not reconciled by deleting files, rewriting ledgers or weakening the baseline rule.

Validation separates normal setup, known failure and explicit retry, cold unknown outcomes, Stop/late callbacks, unchanged-gate rejection, real baseline mismatch, and actual repair reuse. Isolated process/transport faults preserve the original real setup result before obstructing, truncating or withholding delivery; they never inject successful acceptance or edit native history. Repair acceptance and source hashes are checked independently of any parent-model completion message. Full parent return/dependency acceptance remains covered by its separate native consumer and original production scope, not inferred from this setup fixture.

A source review also identified a reachable mixed-ready DAG: A needs repair while C, depending only on accepted B, is independently ready. Dispatch selects the repair group first and leaves ordinary ready producers unchanged for the next checked dispatch. Strict repair configuration validation still rejects mixed configuration input; it no longer blocks the entire legal DAG by collecting both kinds into that input. The finding is source-based unless separately accompanied by an actual old-binary reproduction.

Explicit Continue after a known preparation block may also recover an existing interrupted dependent job from its original preparation. This is a narrow exception to leaving unrelated interrupted children inert: the original repair participants' terminal, registration, hashed dispatch and saved assignment must identify one unchanged configuration; a bounded scan must find exactly one matching ready setup request/result and the original ledger. The existing dependent child's parent/conversation, Issue/request, operator, complete approval, design order/title and scope must match, with an original ready job in both that request and the fixed configuration. Missing, ambiguous, changed or unknown identities remain blocked. No producer is created from extra configuration jobs, and no assignment, execution or terminal is invented for an unstarted child.

The host records a prepared_job_reference and queues that existing child only after successful batch registration. Failure restores the old records and preparation gate. Configuration bytes, source references and current model/runtime/capacity are checked again before dispatch; the runner receives the original expected configuration hash, verifies the original prepared checkout, and retains its actual ticket/resource/lease/intake checks. An existing execution ticket is reconciliation, not permission to replay. Ordinary new jobs cannot inherit this recovered configuration. The setup ledger and parent baseline are never rewritten or recaptured.

Cold startup loses in-memory independent acceptance context. For an already accepted prerequisite in this explicit recovery, the existing original-terminal restore and fresh independent review path is used; its prior acceptance is archived, not reused as a new verdict or erased from history. Repairs keep their original lineage and budgets. The dependent job still uses the current confirmed design's dependencies and requires fresh acceptance-current receipts for every prerequisite; an empty dependsOn array in an old setup configuration does not bypass those checks. Native validation covers a real UID addition, known block, cold Continue, repair/review and dependent-job release, plus changed-configuration rejection. This extends the existing native implementation and shipped runner only; rollback retains all attempts, approvals and original receipts and requires reconciliation of unknown execution outcomes.

In the same live session, an existing matching verified review context and acceptance remain intact and still undergo fresh dependency currentness. An existing unknown or superseded context is not cleared to force another review. Once the recovered dependent job has an actually verified terminal, its prepared reference is archived with that terminal and removed from the active unstarted-job field. A later eligible corrective review therefore enters the ordinary strict repair lineage; unknown or failed terminal binding does not consume the reference. The controlled native scenario also exercises this dependent job's own correction and subsequent independent acceptance.

Legacy hosts may have queued an eligible repair before preparation attempts became persistent. Explicit Continue recognizes only the original still-pending predecessor: unchanged output and terminal, registration and hashed dispatch, bound independent review and archived repair_queued context for the same parent conversation, current approval/operator, original budget and continuation identity. The original runtime configuration remains mandatory. A newer dispatch for that predecessor or an incomplete preparation result requires reconciliation; missing new metadata alone proves nothing about execution. This path neither invents an old preparation record nor clears repair lineage. Its existing original dependent jobs use the same strict prepared-reference recovery. The compatibility consumer obtains these records through an actual old native binary with explicitly recorded current isolated host tools, then exits normally only after actual preparation results and process observations are complete before starting the candidate. It does not delete history fields or claim to replay a complete old installation.
