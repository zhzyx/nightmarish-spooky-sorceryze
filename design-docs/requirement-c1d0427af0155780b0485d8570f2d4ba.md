## 原始需求与目标

用户原话：“当打开引擎，如果用户没配置python、node、git之类的配置，对话回应为gonggong系统阻塞。所以我刚刚去外部ide调试配置的。我现在希望，如果发现是配置问题，则触发本地配置点火器，不被阻塞，能直接在编辑器内进行本地环境部署。”

现状（已核实）：

- `editor/docks/ai_chat_gonggong.cpp`：`_begin_gonggong_context` 在 `gonggong/workspace` 或 `gonggong/python` 为空、或 `tools/gonggong_bridge.py` 不存在时提示“GongGong 未配置”；`_poll_gonggong_context` 在桥接 `chat`/`issue-agent` 返回 `ok:false` 时置 `gonggong_status="blocked"` 并提示“GongGong 阻止本次发送：<error>”。
- `customizations/components/godot-host/bridge.py` 的 `diagnose()`（`doctor` 动作）已检查 node/git/框架/准入/谛听数据，但未显式检查 python，也不把“本地环境缺失”与其他阻断区分开。
- `tools/install_gonggong_runtimes.py` 只覆盖 Windows（`python.exe`/`node.exe`/`cmd/git.exe`，把既有运行时复制到 `project/runtime`）；本机为 macOS，无对应本地部署路径。

目标：本地环境配置缺失（python/node/git）时，编辑器不再以“系统阻塞”终止，而是触发“本地配置点火器”，让用户在编辑器内完成本地部署并继续对话，无需外部 IDE。

## 范围与非目标

范围：

- 检测本地环境（python/node/git）是否配置，并把“环境缺失”与“框架/准入/数据校验失败”区分开。
- 编辑器在环境缺失时进入“配置点火器”，列出缺失项，取代“系统阻塞”。
- 点火器：用户选择组件（python/node/git）与安装位置（默认项目本地），明确授权后执行部署。
- 部署后重跑自检（doctor）；自检通过 + aichat 正常完成一轮视为成功并恢复对话。
- 提供回退：卸载已装组件／还原环境变量，保留日志与恢复入口。
- recovery state workspace 记录已装组件清单、环境变量变更、日志与恢复入口。

非目标：

- 不自动安装；无用户授权不执行任何部署/卸载。
- 不放宽框架准入、谛听文件回执、真实 Issue 绑定门禁；自检通过只表示“环境就绪”。
- 不处理 GitHub CLI（gh）登录与仓库权限（仍由用户在终端完成）。
- 不改变冻结的共工纲领；点火器属于 Godot 宿主接入层，不写入核心框架。
- 首批不默认扩展到其他平台/发布包（见依赖及风险）。

## 设计方案（技术设计）

组件职责：

1. 检测/分类（`bridge.py`）
   - 扩展 `diagnose()`：新增 `python_available`（校验当前进程 `sys.executable` 与 `GONGGONG_PYTHON` 可执行性），保留 node/git；返回机器可读的 `environment_missing` 列表，与 `blocking_checks` 中框架/准入/数据类检查分开。
   - 让 `chat`/`issue-agent` 在因环境缺失失败时，错误里带 `environment_missing:[python,node,git…]` 标记；框架/准入/数据失败不带此标记，仍按“阻止”处理。

2. 组件注册表（可扩展）
   - 每个组件：id、显示名、检测命令、安装方式（项目本地/用户级）、卸载与还原方式、成功证据命令、日志位置。
   - 初始注册：python、node、git；后续新增只需加条目，不改点火器主流程。

3. 点火器执行动作（`bridge.py` 新动作，异步子进程，不阻塞 UI）
   - `environment-check`：只读返回缺失项与可选安装位置（复用 doctor 扩展）。
   - `environment-deploy`：按用户选择的组件+位置、经授权后执行部署；写入 recovery state workspace（清单+环境变量变更+日志）。
   - `environment-rollback`：卸载已装组件／还原环境变量，保留日志与恢复入口。

4. recovery state workspace
   - 位置：默认项目本地（如 `project/runtime/state/`，与默认安装位置一致）；不提交机器绝对路径、凭据或缓存。
   - 内容：已装组件清单（相对路径+sha256）、环境变量变更记录、安装/卸载日志、恢复入口（回退命令/标记）。
   - 用途：重启后恢复点火器状态、失败回退、审计。

5. 编辑器交互（`editor/docks/ai_chat_gonggong.cpp`）
   - 桥接返回环境缺失时，进入“配置点火器”引导状态（不调模型、不执行工具），列出缺失项，让用户：选择组件 → 选择安装位置（默认项目本地）→ 明确确认授权。
   - 授权后触发 `environment-deploy`，完成后重跑自检并继续原消息；自检失败或用户拒绝/取消则停在该步并保留原消息，不残留半绑定状态。
   - 回退入口在点火器状态或 GongGong 页提供，执行 `environment-rollback` 后回到未部署状态，保留日志与恢复入口。

6. 成功判定
   - 部署后重跑 `doctor`，`environment_missing` 为空且环境类检查通过；
   - 再用原消息完成一次 aichat 上下文装配/模型回复（`context_ready`）即视为部署成功并恢复对话。

## 依赖及风险

- 现有 `install_gonggong_runtimes.py` 为 Windows-only；本机为 macOS，点火器需定义 macOS（及 Linux）安装路径（如 Homebrew／预置运行时／用户自选可执行文件），这是本单的主要实现工作量与风险。
- 项目本地安装需要可靠检测命令（`shutil.which`／版本命令），并记录 sha256 与来源，避免与系统环境混淆。
- 回退依赖“部署时记录的清单与环境变量变更”完整；若部署被外部中断，recovery state workspace 可能不完整，需设计为原子写入（先写临时文件再替换）。
- 不提交机器绝对路径、凭据、缓存到 Git；recovery state workspace 的清单可选择性提交，日志默认不提交。
- 点火器不得移除框架校验（不能通过移除准入检查恢复聊天），回退也不得降级门禁。
