# macOS 原生编辑器和模板网络测试

#471 跟踪天枢 Mac 验收后完整引擎测试暴露的两项失败，原运行 42379241429，修订 9dee6d0468c88fc0b5e0313ab5b2541fb84e830b。原工单、两个作业和工件可从 [GitHub](https://github.com/zhzyx/nightmarish-spooky-sorceryze/issues/471) 回读。

编辑器的 TCPServer 测试写死回环端口 12345，监听与连接辅助函数忽略调用者的地址和端口。停止自己的监听器后若其他进程在该端口接收连接并关闭，新客户端可进入 STATUS_NONE。原 CI 只给出 0 与预期 3，无法据此确认当时谁占用了端口。改为让系统分配监听端口，客户端使用实际端口，停止前保存目标。仍检查拒绝连接、主动断开和成功传输。

原模板的 DedicatedServer 两客户端用例在拒绝新客户端后崩溃。ENetConnection 清理已断开 peer 时删除链表元素后又读取该元素的后继。改为先保存后继再删除当前元素。继续运行完整套件时发现标准发布模板不接受重启探针的 --path 和 --script。支持路径覆盖的构建仍逐字校验 PID 和参数；标准模板使用自身支持的 --version 验证两个回退启动分支的 PID 和退出码。显式外部可执行文件测试仍校验完整参数回执。

验收在 macOS arm64 对照原始工件、运行定向和完整模板及编辑器单测，以签发候选的 macOS 完整构建作业核对发布结果。保留原 CI 中未能从历史日志确认的环境条件。

第一次完整云端复验 42400699283 在动态端口上再次得到 STATUS_NONE。随后在同型号 macos-26 runner 的独立回环诊断 42403579218 中，固定端口和动态端口各 15 次，针对已停止的监听器重复 connect 均返回 EISCONN，同时 SO_ERROR 为 ECONNREFUSED。之前的实现把 EISCONN 当作成功，后续 EOF 使状态进入 NONE。现在 UNIX TCP 在首次非阻塞连接返回进行中后，等待可写事件并以 SO_ERROR 判断原连接是否成功。关闭套接字会重置等待状态。保留原来的 STATUS_ERROR 断言。
