## 订阅登录首版

本阶段按用户指示使用已有订阅登录。首版从 Godot 工单详情选择 Codex CLI，沿用操作者的 ChatGPT 登录，核对有效认证方式；凭据留在 CLI 管理的存储。首版交付与验收均使用此入口。[OpenAI 官方认证说明](https://learn.chatgpt.com/docs/auth)

基线中 AIChatDock::_start_codex 每轮取消旧 CLI、序列化完整消息与当前可用工具，再启动 tools/codex_cli/godot_bridge.js。桥接器以 exec --json --ephemeral 运行，结构化结果给出待执行动作，Godot 执行后进入下一轮。相邻的增量消息代码用于其他 CLI 路径；Codex 桥接器的 app-server 当前只用于列模型。

优先复用编辑器现有工具授权和快照处理。按工单、工作者、候选、后端配置和治理修订绑定会话。首轮记录 CLI 返回的线程 ID 和已接收前缀；随后只发送新增用户消息、工具结果及变化的上下文。授权变化、历史改写、图片变更须校验边界。上下文与回执缺失时按本地日志核对，保留未决副作用。明确指定线程 ID 可避免串到其他工单。exec resume 可以验证跨进程会话连续性，每轮启动数仍需实测。[OpenAI 官方非交互运行说明](https://learn.chatgpt.com/docs/non-interactive-mode)

同一工作者的连续工具回合应复用健康进程，或将独立且已获准的读取合并处理，分别统计节省的启动与往返。常驻通道启用前要验证用户配置隔离、禁用原生写入、宿主审批、当前候选与只读审查约束。按请求代次将真实接收、文本、工具等待和轮次终态推送到原工单，过滤取消后的迟到事件。审批、实际执行结果、模型接收工具结果分别留证。

操作执行前持久记录动作身份及意图，执行后保存原始回执引用和回传状态。重启后优先以相同动作查权威执行端。已完成则复用结果，执行中则恢复观察，发送后结果未知则保持待核。新消息继续指向原工单和工作者，保存到可接续的位置。对不可查询且可能已生效的动作保留人工核对入口。后台长任务以真实任务 ID 追踪，界面显示最后一次真实事件及时间；进程退出、取消请求和业务完成分别保存状态。谛听写入如可延期则保留待补回执，与模型调用分别重试；权限、准入或动作依赖未满足时暂停对应操作。采集脱敏，不写凭据。

## #599 工单回读与批量工具

热缓存下，#607 的已绑定工单每轮依次核对 Issue、当前账号和仓库关系。新宿主使用安装树的门禁在同一请求里回读 Issue、当前账号和有效写权限；普通公开读权限继续核对显式协作关系。直接创建的工单用同一份受信原文复核开工回执。原文留在宿主本地进程，采集写入校验摘要。旧候选保留其工单、框架和目标目录。

Windows 上对同一工单交替做三组实际回读，旧实现中位数 3.846 秒，新实现 1.958 秒。真实编辑器一次请求读取 9 个独立文件，模型首轮提出 9 次读取，第二轮准确答回复合结果。恢复日志与普通历史可保存最多 32 个只读调用；混合或写入批次仍限 8 个。机器、单次运行与测量范围见 data-collection/tianshu-bound-chat-599.json。

## #594 原命令的重启恢复

Godot 在启动工单命令前写入可核验的调用记录。编辑器意外退出后只观察原守护进程；结果必须匹配同一会话、候选、调用摘要与当前授权。工具结果和消费标记同时写入会话历史。观察时可以停止；原命令已产生的副作用不会重放，未保存的标准输出标为不可用。准确候选、跨账号和二次强退用例见 data-collection/tianshu-command-recovery-594.json。

## #599 Windows 订阅常驻会话

天枢可以通过现有 Codex 登录保留一个只读 app-server 进程。每次模型请求前仍回读工单；只在原账号、工单版本、授权、候选、模型、历史及已接受的上轮回复一致时，向原线程追加消息。用户的问题与主机指令按最新值传递。不能验证的配置使用兼容路径；已经提交模型的请求失败时不会自动重发。关闭编辑器会终止其正在启动或运行的模型进程。最新真实工单的文件结果与两次追问用时分别为 56.803、13.379、8.154 秒，后一次确认增量复用；与宿主原生约 4 秒仍有差距。多轮现场数据见 data-collection/tianshu-subscription-session-599.json。

## #594 批准前退出（#617）

在用户看到命令、还没有批准时退出，重开后天枢会重新核对原工单、账号、源码候选和调用，为原建议提供新卡。旧卡不能授权。审批完成、取消、结果未知和权限变化分别处理。授权改为自动也不会跳过已经在等人批准的决定。命令工作目录失效时，整批停留在原步骤。验证见 data-collection/tianshu-pending-approval-594.json。

## #620 Windows 新工单的首次回执

一次真实读文件工单中，天枢收到模型回复后还等待约 21 秒才开始执行工具。对同一批历史记录采样发现，开销集中在逐个打开文件。现在只在 Windows 大数据集的首批实际读取较慢时，最多使用 12 个线程，在有限内存中预读；仍逐字节校验、检查完整引用关系，再写入原回执。

同版本数据和同一事件在四个新检出目录交替测试：原版首次校验 21.328、21.359 秒，新版 3.281、3.141 秒，摘要相同。Godot 中沿用已有 Codex 登录，读随机文件及两次追问实测 44.016、13.250、9.259 秒，均无额外点击。短追问仍慢于原生对照；今后分别计量模型、身份回读与回执时间。完整结果见 [现场与对照记录](../data-collection/tianshu-cold-receipt-620.json)。

### #706 的 Windows 订阅追问

工具轮完成后，编辑器将对话历史收敛为用户问题和已接受的终答。首次追问沿压缩后的历史重建模型会话。第二次追问只有在身份、授权范围、历史前缀和编辑器已接受的回复均通过校验时才增量发送。

宿主每轮重新生成 mandate。订阅桥核对全部系统消息，只在规范 JSON 中唯一的 `outcome` 字段发生变化时单独发送该字段。其他系统消息变更仍随请求发送完整指令。模型服务报告上下文压缩后，下一轮从完整的宿主输入重建。若压缩发生在仅发送 `outcome` 的一轮中，桥会丢弃该轮终答和动作，返回 `CONTEXT_COMPACTED`，可从原工单重新发起。传输回执记录重建原因和本轮输入文本的 UTF-8 字节数。

按同一组九个只读文件轮换原生 Codex、当前输入框和重新打开已有对话三个入口。每个入口检查九个值的顺序、两个短追问的逐字答案及完成回执，重新打开对话另计进入耗时。样本、分段计时及失败记录见[工单实测数据](../data-collection/tianshu-706-followups.json)。CodeBuddy 官方账号认证沿用 #662，独立 HTTP API 沿用 #593 的延期决定。
