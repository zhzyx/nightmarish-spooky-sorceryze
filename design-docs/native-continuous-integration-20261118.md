# 多 Agent 持续提交与同产品发布接续

需求 ID：native-continuous-integration-20261118；父 #1444，承接原始 #1382 用户要求。优先级是 AI 工作链路效率，所有路径以仓库根解析。用户已授权推翻 Git 权威及底层方案，但保留原有角色与 AA 渲染能力。

现状核验：#1466 已把不可变贡献收件与 product channel 发布分开；生产者原输入不跟随 main。当前 NativeIntegration 将 tasks/base/expected 固定，CAS 失败依靠安装者另给新计划。250 贡献汇为一次发布不等于 250 个持续到达的独立工作都能自动完成。简单只更新 expected 而保留旧产品 base 可能丢掉其他已交付内容；把旧 integration-* 元数据一路带入会扩张实际输入与检查。现有能力尚不足以宣称满足用户目标。

目标架构：提交入口固定原始任务、对象、模块版本和读写依赖，持久接收后原生产者退出并可领取下一任务。验证与接收按实际影响范围进行；无关产品版本变化不能触发原模型重做或全仓库重读。合契负责在事件驱动下把已验证原件组成产品快照；阎罗只对精确快照独立验收发布。产品发布的短原子选择不得变成所有提交/模型执行的长全局锁。真实同对象冲突与依赖/ABI 变化单独处理，不能以最后写入胜出、忽略语义检查或谎报完成求速度。

1. 用当前真实 NativeWorkflow/Candidates/Integration/Release 重现至少两组不同修改竞争同产品同channel：第一组发布后，第二组必须自动接续到包含两组修改的正确快照，无须改原任务、重启原生产者或用户手改计划。普通 receive/produced 与业务 accepted/done 清楚区分；不能早关 Issue。
2. 设计并实现有界、可恢复、事件驱动的接续机制。可采用每产品/通道短租用的单一发布责任者与公平固定批次，或经论证的等价方案；源码实现前提交具体权威数据、状态、并发/故障/公平性设计给根责任者审查。不新增定时扫描，不允许用时间过期重放未知外部执行；同产品短必要发布串行与提交/模型长时间等待分离。持续新输入不得饿死已经接收的贡献，单批次数量、资源和每次事件工作量有界。不同产品可独立推进。
3. 新快照从真实已选产品读取原件并三方整合，保留所有已经交付的无关修改/删除；相同对象不同值、删除与更新、依赖变化仍显式阻塞受影响内容。无关已检查对象/模块沿现有精确输入缓存复用。最终产品确实改变时，必要联合语义/ABI/渲染检查仍执行；记录实际调用次数，不能把“无需重复模型”冒充“无需任何检查”。
4. 权威接续关系和操作意图持久化，幂等事件、双驱动、宕机在发布前后及领域接纳前后可回读恢复；源任务换版、撤权、检查安装变化、未知审查/进程均保留现有阻断。新计划/批次必须被当前安装者与权限授权，不能自签任意代码/审查或扩大任务写范围。旧有效工作流/发布 API 保持兼容或明确安装迁移。
5. 当前版本的 integration-* 检查清单是安全输入，不按名字通配删掉。将活动产品内容与历史验收证据正确分层：保留原要求、原检查和历史出处可验证性，同时避免每次发布把全部旧计划递归复制进模型输入/活动产品。设计须支持旧发布读取；元数据不能冒充业务模块，也不能破坏依赖图。
6. 使用真实数据库、检查进程、工作流及事件入口验证连续到达、相同/不同模块/产品、冲突、撤权、重启和失败回读；至少250个固定原件分多批/多次实际发布，包含发布过程中继续到达的贡献，证明每原生产者只执行一次、无丢失/重复验收、无无关全局阻塞。报告实际每批排队/检查/发布耗时和缓存命中，独立审查，不能预先承诺吞吐或把250个在途解释为250个模型同时运行。
7. 本项不改渲染/原生头文件，不削弱联合质量；模型路由继续司南，冲突归合契，交付归阎罗。现有 #1481 远端与 #1486 模型试验在其冻结树独立进行，不修改其源码或占用。不接管 #951 控制器与 #1343 渲染任务。

新增部分属于现有宿主工具，记录真实输入、持久状态、宿主接口和停用回退（保留原件/历史/未知占用），执行实际构建边界和独立验证。根负责正式交付，不能以规划、局部通过或 PR 合入替代父目标完成。

## 2026-11-18 根审定的实施约束

持续入口是 NativeIntegration 的显式安装扩展，默认旧 API 保持原语义。安装策略固定 tenant/product/channel、bootstrap base、checks、max_batch（1..32）、请求溯源；成员默认可独立交付。SQLite FIFO 接收与固定 batch 是权威，不按到达的新输入改写在途快照。每次事件至多执行一批；每产品/通道非阻塞 OS 锁仅用于发布驱动，生产、收件、单件检查不拿此锁。OS 锁随真实进程退出释放，无时间租约偷取。未知检查/审查/解析器状态沿原入口阻断。

后继从真实 selected 全量业务内容三方合并。已知 CAS 失败先回读发布 request；确认未发布且外部结果已知才建立新 immutable plan，新快照重新检查与独立审查。连续发布责任者由安装层独占；不承诺任意非协同外部写者无限写入时仍无饥饿。冲突或撤权成员保留失败回执并隔离，可兼容任务继续；本入口不接受需原子交付的成员组。

历史清单只通过真实 historical selection、accepted integration、精确 candidate/module/revision 识别；存在业务依赖时拒绝剥离。当前 manifest 保留当前完整 originals 与 predecessor selection 引用，历史原始条件由权威 history 读取接口提供，检查安装必须能读取引用；不按名称删除业务模块，不递归复制历史文本。持久 batch/result/error/metrics 与旧计划均保留。停用持续安装不销毁原件、历史或未知占用，恢复原固定计划接口须显式处理在途批次。

复用 editor-dependency-handoff 已验证方法：await-terminal-observers、reconstruct-worker-outcomes（真实终态/未知不重放），bind-consumer-release（精确输入与独立回执），review-context-and-source-evidence（历史上下文不能替代当前精确检查）。反例是运输成功、文件仍在或旧候选审查不证明新快照验收。

### 实施后的历史输入与容量

安装策略必须明确 history_refs：可选 first、predecessor 或精确已验收 release ID，最多32项。本批 freeze 将实际 required_history 固定进 manifest；总发布次数没有32上限，真正超过单次检查容量则拒绝安装。原件和所有历史计划仍通过鉴权 history 方法按任意精确 release 查询。当前质量检查负责所有活动内容，历史选项不能用来省略实际必需标准。最终实测使用 first+predecessor，超过32批后仍实际读取首批原要求。

归档 criteria 每个 release 只写一次。本候选的独立输入视图只复制安装者指定的少量文件，不能使用可写 hardlink 共享归档。runner 对视图和归档在检查前后验证字节，固定引用集合与provider源码/持久根/容量进入精确候选与check context。检查污染视图必须失败且不能改变归档。缓存命中前也核验历史绑定；无关活动内容检查仍走原 EvidenceCache。

当前可选持续安装的显式限制：同一产品只能映射一个安装channel；成员必须可独立交付，不声明原子组；未知检查或审查保留产品发布批次占用，其他产品与原生产收件不受该发布锁影响。已有固定计划API兼容；绕过持续责任者的旧发布可造成一次已知CAS接续，不承诺无限非协同写者的公平性。历史provider视图材料为宿主工具输入，不加入业务模块依赖图。停用须保留未知占用与SQLite历史。

### 多成员、完成观察与失效成员隔离

持续策略显式指定 coordinator，不能把第一位提交者当作产品所有者。提交者与协调身份必须具有当前同租户 editor/admin 权限；每份原任务继续核验本人的源授权与生产身份，协调身份逐件核验授权。caller不能选择协调身份，撤权不触发隐式转移。不同成员共用该产品channel的FIFO。

HTTP integration-continue 接收有界事件标识，native_continuous_drives 持久保存请求与终态。宿主用真实驱动 Future 绑定在途执行；publisher_busy 别名指向原责任者。integration-await 只观察真实完成或回读已持久终态，HTTP前后验证认证；丢响应不重放continue。重启后没有真实执行所有权且无持久终态时返回unknown，保留原intent，不能靠generation变化认定执行已结束。不同宿主的锁占用若没有可观察物理owner，仍明确unknown，不谎报自动跨宿主接续。

freeze后个别原任务换版或撤权时，仅在没有已发布request、未知check/review/resolve/execute意图的情况下，将失效成员及失败原因保留为blocked，其他原件回到队列，形成新的精确快照。已经发布但领域接纳未落库、或外部执行结果未知时保留原批次。检查与发布阶段耗时持久记录；FIFO等待从真实入队时刻起算。

本次源级实测以确定性Python生产者、真实SQLite和owned check进程验证，不调用模型、不替代真实渲染质量验收。50个真实同租户成员各5份贡献、36次实际发布，检查包括每个变化产品的联合检查以及一个固定对象的缓存复用。运行入口为 `customizations/components/tianxuan/sinan-workorders/native_continuous_acceptance.py --run-name <全新短名称>`；运行目录限定在仓库根解析的 `work/native-continuous-integration-probes/`，最终回执在 `data-collection/native-continuous-integration-1488.json`。检查注册和安装配置属于测试夹具，不能冒充生产安装授权。
