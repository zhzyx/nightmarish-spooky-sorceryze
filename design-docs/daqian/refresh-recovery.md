# 天枢刷新失败后的个人视图恢复

父项 #442 的首屏与恢复验收。当前 Windows 实验中，真实仓库冷启动从选择天枢到 106 单可浏览为 12.076 秒；一次热启动未显示工单，随后在同一隔离配置复测为 2.775 秒显示缓存，25.483 秒取得完整回执。另一次宿主分段测量含 105 单，资格读取 2.535 秒、历史看板读取 9.152 秒，当中两个并行 GitHub 请求累计 9.397 秒。单次热启动失败的原因未知。

可重复构造的失败路径包括 GitHub CLI 的 TLS handshake timeout 被归为通用命令错误，从而丢弃有效缓存资格；项目层断网后显示“离线个人快照”时仍可能保留项目数据。重做刷新恢复分支，瞬时网络和服务错误允许已有账号按有效期读取个人快照，真实拒绝授权立即失效。在线后台更新中，已验证会话直接读取看板并核对读前读后身份，账号变化须重新鉴权。重复刷新等待同一次完成事件。

验收使用隔离 Windows 原生编辑器：账号切换、明确撤权、掉线前已进入项目图、本人及历史缓存、恢复上线、重复刷新。写入继续经过原宿主准入。记录冷/热首屏实测和完整后台回执，两者分别报告。

## 更新

Windows 定向回放先发起项目读取，在返回前发起个人读取，再按项目、个人顺序放行。旧实现会把项目图替换为个人工单。范围切换确认时递增版本后，相同顺序保留三条项目工单；随后断网会回到本人快照，恢复联网继续读取本人范围。旧版本也复现了 TLS 错误后丢失个人快照。两项均用后台原生控件验收。

与 #452 的 main 接收点集成后，Windows 编辑器 SHA256 为 a880c7056ff71007c6bb05d5190ba0c97d8780903190ab95ff51f6b73ccef482，同一 graph 场景连续四次通过。真实仓库 107 单实测，冷启动 14.805 秒出现完整工单，热启动 1.255 秒出现可操作快照，9.941 秒取得完整回执。网络与样本数有变化，前后耗时保留为各自观测。
