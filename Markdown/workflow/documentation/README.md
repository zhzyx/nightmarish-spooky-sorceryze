# 文档与路由迭代规则

本细则约束规范的新增、拆分、合并和废弃，目标是让规则始终位于最具体且最容易被发现的位置，同时避免目录和模块无限增殖。

## 1. 新增规范：先找细则，不先建文件

新增规范前必须按以下顺序定位：

1. 在根 `AGENTS.md` 找到任务所属模块。
2. 沿模块 `README.md` 找到与规则主题最匹配的子模块。
3. 进入具体细则，将新规则插入对应章节，并同时更新受影响的示例、检查和来源索引。
4. 同一规则已有正文时只修订原正文，不新建平行文件，也不在父级复制一份。

**默认动作是编辑现有细则，而不是新建 Markdown 文件。** 只有现有细则无法容纳其独立任务边界时，才考虑新增子模块；确属全新领域且现有顶层模块均不匹配时，才新增顶层模块。

新增模块或子模块后，必须同步登记父级索引；新增顶层模块还必须登记根路由。

## 2. 何时允许拆分

只有同时满足以下条件才拆分：

- 新主题有清晰、独立的任务触发条件，可以单独加载而不必阅读其他并列细则。
- 原文件已因多个独立主题混杂而难以定位或维护。
- 拆分后有明确的权威正文归属，不留下两份竞争规则。
- 父级索引、来源索引和受影响链接能够同步更新。

只有少量规则、一个孤立示例或一次临时任务，不构成拆分理由；先保留为现有细则中的章节。

## 3. 颗粒度过碎时必须合并

发现以下任一情况，应检查并合并相关模块：

- 多个模块的任务触发条件、适用对象或责任边界基本相同。
- 完成同一类任务时总是需要同时加载多个并列模块。
- 大量叶子模块只含一两条规则，目录层级反而增加查找成本。
- 父模块长期只有一个没有独立边界的子模块，索引只增加跳转。
- 不同模块重复维护同一规则、示例或检查清单。

合并时优先归入最近的共同父模块或职责更明确的现有模块，用章节保留内部结构；不为了保留原目录形态而留下无内容的转发层。

## 4. 合并与废弃流程

1. 先确定唯一保留的细则和权威正文，再整合重复或冲突内容。
2. 保留仍有效的规则、来源与历史链接；历史证据不因为模块合并而被删除。
3. 更新根路由、各级 `README.md`、`sources` 索引及引用旧路径的文档。
4. 删除已被完整接收的重复正文和空路由；确需兼容外部链接时，保留明确的单一转发说明。
5. 检查相对链接、代码围栏、尾随空白和遗留路径，确认没有失效入口。

## 5. 每次路由迭代的最小检查

- 新增规范是否已进入最具体的既有细则。
- 是否存在可合并的过碎、重叠或重复模块。
- 每条路由是否能从根文件逐级到达唯一正文。
- 是否只加载当前任务所需模块，而非全量文档。
- 原始规范、历史证据和当前执行摘要是否仍清楚区分。
